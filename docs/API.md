# API contract

JSON over same-origin `/api`. Authentication uses `shaikhs_session`; protected reads use the current active database user. Writes require matching Origin (mandatory in production). Errors use `{error:string}`; checkout validation may add `details`. Error status taxonomy and durable rate limiting are not yet uniform.

## Checkout

Required `Idempotency-Key`: 8–128 ASCII letters, digits, `_` or `-`. Retain the key and intent across uncertain failures. Keys are customer-scoped. Changed intent with an existing key returns 409; identical replay returns the existing order.

Body: `{restaurantId,deliveryAddress,notes?,paymentMethod?,items:[{productId,quantity}]}`. Address 8–400 characters; notes ≤500; 1–30 items with unique product IDs and integer quantity 1–20. CASH_ON_DELIVERY is default; ONLINE is rejected. Client prices are ignored.

Server reads current restaurant/item availability and prices in a transaction. Exact Decimal subtotal, delivery fee (35 below 499, otherwise 0) and 5% tax rounded half-up once to paise form the total. These coded business/tax rules require review before launch. Initial status history is written with the order.

## State / operational limits

PLACED → ACCEPTED → PREPARING → READY_FOR_PICKUP → PICKED_UP → DELIVERED. Cancellation is allowed before READY_FOR_PICKUP. Restaurant actions require ownership; rider pickup/delivery require assignment; admins follow lifecycle rules. Status changes compare the observed status and rider assignment, then write history in the same transaction. Admin revenue sums only PAID, noncancelled orders. This does not implement COD collection or settlement recording; no settlement ledger exists. Consult the test report for verification limits.

No cursor/page parameters exist: order/user limits truncate results. No explicit rate limits or generated OpenAPI contract. Idempotency keys apply to checkout; other mutations rely on state validation. Do not publicly cache private responses. Payment webhook/refund endpoints do not exist.

## Verified contract additions

- GET /api/restaurant/status: RESTAURANT owner only; returns {restaurant:{id,isOpen}}, 403 forbidden, 404 missing profile. Prevents the UI from assuming a closed restaurant is open.
- GET /api/orders now includes statusHistory:[{status,createdAt}] in chronological order. Historical orders are not backfilled with invented events. Responses contain paymentMethod/paymentStatus and deliveryAddress; existing role/tenant scoping applies.
- GET /api/admin/users metrics.users is an actual database count, independent of the 200-account list cap. metrics.revenue is an exact Decimal string, the gross paid noncancelled order total (including configured tax/delivery fee), not net profit. Users include deliveryProfile.isOnline for assignment choices.
- POST /api/admin/orders/:id/settle: ADMIN, signed session and same Origin required. Body {amount:string,reference:string}; amount has up to eight integer digits and two decimal places, reference 8-100 ASCII letters/digits/hyphen/underscore. Only DELIVERED + CASH_ON_DELIVERY + PENDING orders qualify and amount must equal server total. Transaction atomically marks PAID and inserts CodSettlement. Identical amount/reference replay returns the same receipt; conflicting order/reference returns 409. 400 invalid, 401 missing session, 403 role/origin, 404 absent order, 409 amount/state/reference conflict, 503 operational failure. Returns {settlement:{id,orderId,amount,receivedById,reference,createdAt}}. No provider money movement occurs.

Idempotency and receipt keys should be retained on uncertain failures. Delivery status alone does not acknowledge receipt of cash. ONLINE remains disabled; provider webhooks/refunds are unimplemented.

Payment body limit 16 KiB; authenticated payment routes: 30 requests/account/minute. Errors: 400 malformed/validation, 401 missing login/signature, 403 role/Origin, 404 unknown or another customer's payment, 409 state/amount/binding/event conflicts, 413 size, 429 throttle, 503 disabled configuration/provider/database/unresolved order. Unexpected provider errors are sanitized. Unique event rows are not committed on transaction failure: provider must retry; reconcile missing order binding first.

GET /api/admin/users additionally returns metrics.paymentReviews and metrics.pendingRefunds. Verified revenue excludes cancelled, refunded, unpaid and review-flagged orders; values remain exact decimal strings. It is gross verified collection, not net profit. Paid cancellation writes a refund-required audit and remains an obligation until processed refund. Partial refunds/additional captures are explicitly flagged and excluded until reviewed, rather than misreported as fully reconciled.

Auth requests are bounded to 16 KiB; registration passwords max 72 UTF-8 bytes. Durable fixed windows: login 10/account/15 min + 120 global/min; registration 5/email/15 min + 30 global/min; 429 with Retry-After. Counters use hashed identities, never untrusted forwarded IP headers. Global thresholds suit a controlled small launch; upstream abuse protection and retention operations still need deployment review.

Refund obligation count includes paid cancellations and any paid online order with REQUESTED/FAILED full refunds. Unresolved provider creation is flagged for review; successful verified receipt binding clears only the creation review flag. Unbound non-CREATING states stop for manual review rather than recursively issuing provider lookups.

## Customer Checkout additions
GET /api/payments/config is public/no-store and returns only {enabled,mode:test}. enabled requires valid TEST configuration AND RAZORPAY_SANDBOX_VERIFIED=true. POST /api/orders now permits new ONLINE orders only through that gate; identical prior checkout replay remains safe even after the gate closes. New unverified ONLINE requests return 422.
GET /api/payments/status?orderId=... is owner CUSTOMER/ADMIN authenticated, rate-limited and no-store; it returns minimal order state and payment DTO, 404 for another customer's order. Reconcile/verify DTOs can include awaitingCapture=true for created/authorized provider attempts; clients must not open another checkout while this is true. SDK handlers never directly set PAID. See RAZORPAY_SANDBOX.md for activation and acceptance.

Direct POST /api/payments/orders is gated as well (503 while unverified, after owner authorization). Operator bootstrap before attestation is confined to npm run sandbox:provider with a guarded local disposable URL and SANDBOX fixture. No public HTTP bypass exists.

Release endpoints: GET /api/health/ready returns no-store 200 only when required migration history is complete, otherwise generic 503. POST /api/monitoring/client-error accepts only `{area: "route" | "root", fingerprint?: SHA256_HEX}` with normal Origin protection, bounded body and throttling; returns a generated reportId (202), invalid-body 400/413 or throttled 429. No raw exception text is accepted. Monitoring references support host-log correlation, not external alert delivery.

Customer PATCH /api/orders/{id}/status now permits only CANCELLED on the customer's own PLACED order. Another customer's order returns 403; acceptance/already-cancelled state returns 409. Atomic status/assignment/payment compare-and-set records one actor/history event; paid cancellations retain verified payment status and record a refund obligation, never an invented refund. Restaurant/admin cancellation rules remain unchanged.

## Restaurant and delivery operations API

GET/PATCH /api/restaurant/status is owner-scoped. Settings include manual isOpen, nullable weeklyHours (seven unique days 0=Sunday; HH:mm open/close and closed), nullable closedUntil (future, at most seven days), and optional expectedVersion. Timezone is Asia/Kolkata; overnight shifts extend into the next day. A closed/manual-paused/out-of-hours kitchen is excluded from discovery and checkout. Existing unscheduled kitchens preserve manual availability. Stale settings return 409.

PATCH /api/orders/{id}/status accepts preparationMinutes (5�180, default 30 on acceptance), reason (3�300 characters, required for operator rejection/cancellation), verificationCode and cashCollected. READY_FOR_PICKUP creates a kitchen-only pickup code. Only an accepted rider assignment can be picked up; the correct kitchen code creates a customer-only delivery code. Delivery requires that code and explicit full-COD acknowledgement. Five handoff verification attempts per actor/order per 15 minutes are enforced. Neither rider confirmation nor any exception marks COD paid; only the existing admin cash-receipt endpoint does so.

POST /api/orders/{id}/operations requires expectedVersion and action: assigned online rider ACCEPT_ASSIGNMENT; assigned rider REJECT_ASSIGNMENT with reason; picked-up accepted rider CUSTOMER_UNAVAILABLE, ADDRESS_ISSUE or FAILED_DELIVERY with details. Open issues block delivery/status changes. Only ADMIN may RESUME_DELIVERY or RETURN_CONFIRMED with a resolution reason. Confirmed returns cancel the order without crediting cash; verified online payments retain a refund obligation. ISSUE_DELIVERY_CODE supports already-picked-up legacy assignments without exposing their customer code to riders. All operations use atomic version/status/assignment checks and durable operational history. Wrong owners/roles return 403; stale/conflicting state 409. Order responses redact pickup codes from customers/riders and delivery codes from kitchens/riders. Codes are app handoff verification, not SMS/phone verification.

## Staff, menu and rider finance APIs

- GET /api/restaurant/context returns owner/staff capabilities. All tenant lookups are server-derived: OWNER manages settings/team; MANAGER handles menu/orders; MENU edits menu; KITCHEN handles orders. Inactive memberships fail every protected request, including existing sessions. One restaurant per staff account.
- GET/POST/PATCH/DELETE /api/restaurant/staff: owner roster, email-bound 48-hour invitation, versioned role/activation change, or invitation revocation. Raw invite token is returned once only in local disposable development environments; only its SHA-256 hash is stored. No email is sent. /staff accepts the token from a URL fragment and removes it before submitting onboarding. POST /api/staff/onboard binds email, enforces expiry/single use, and requires authentication before upgrading an existing customer account; its password is preserved. No public role selection is enabled on ordinary registration.
- GET/POST/PATCH/DELETE /api/restaurant/categories manages active categories. Category deletion archives an empty category; archive/move active dishes first. POST /api/restaurant/menu and PATCH/DELETE /api/restaurant/menu/{id} provide bounded, versioned item editing and archival. Fields include categoryId, name, description, paise-accurate price, imageUrl, available and options (VARIANT absolute unit price, ADDON per-unit surcharge). Missing options are archived rather than deleting history. Checkout requires an available variant where configured, validates option ownership, supports separate configurations of the same dish and snapshots names/prices/options. Existing orders never reprice after edits/archival; retry hashes include normalized selections and fee quote version. Checkout body is bounded to 64 KiB.
- POST /api/restaurant/images accepts raw JPEG/PNG/WebP (matching Content-Type), at most 2 MiB. Sharp validates decoding, pixel count (16 million), animation/MIME, strips metadata and normalizes to <=1600px WebP. Scoped attachment checks prevent using another kitchen's upload in mutations. Public GET /api/menu-images/{id} serves immutable normalized bytes with nosniff. No arbitrary filesystem paths or SVG uploads.
- GET/PATCH /api/delivery/policy exposes public customer fees; only ADMIN may read/update payout fields. Default delivery fee INR 35, free threshold INR 499, rider base INR 25, delivery-fee share 0 basis points. Payout = base + fee x share/10000, rounded half-up to paise. Version conflicts return 409; new checkout snapshots payout/fees, so later edits cannot change existing earnings.
- GET /api/delivery/earnings returns rider-own or admin-scoped earned, pending, available, settled and separate COD collected/reconciled/unreconciled totals. Pending includes available; earned = pending + settled. COD collected requires a rider collection event or admin cash receipt. Histories are paginated in 50-row pages (page/settlementPage, nextPage/nextSettlementPage); totals use a consistent database snapshot and cover all rows.
- POST /api/admin/rider-settlements records a payout already made; it does not transfer money. It accepts riderId, 1-100 unique earningIds and a unique reference. Amount is calculated only by the server from completed, verified/reconciled, unsettled deliveries. Reference hashes bind exact rider/earnings; retries replay safely, competing receipts cannot pay twice, and COD cash is never automatically netted into earnings. This is separate from existing admin COD cash reconciliation.

Checkout compatibility: the browser sends X-Delivery-Policy-Version separately from its stable order intent. Quote validation applies before creating a new order; an existing idempotent replay keeps its original fees. Legacy no-option basket/request ordering and saved retry fingerprints are preserved across this milestone. Explicit body policyVersion remains supported for API callers.

## Saved addresses and postal serviceability

- GET/POST/PATCH/DELETE /api/customer/addresses is CUSTOMER-only and derives ownership from the session. Fields: HOME/WORK/OTHER label, normalized addressLine/landmark/city/state, six-digit Indian postalCode, instructions and isDefault. PATCH/DELETE require id/version. Up to 20 active addresses; customer-row locking plus a partial unique index prevents concurrent default duplicates. The first address becomes default; removing a default promotes a remaining address. Removal archives the address book entry; existing orders keep their delivery snapshots.
- GET/POST/PATCH/DELETE /api/admin/delivery-zones is ADMIN-only. Rules bind restaurantId/postalCode to deliveryFee, minimumOrder, optional freeThreshold, priority and active. An empty freeThreshold inherits global policy; each zone explicitly sets its fee. Highest active priority wins before checking minimum subtotal; equal active priorities for a restaurant/PIN are rejected by the database. Deletions archive/version rules. GET includes restaurant choices/default fee for new rules. Restaurant/staff GET /api/restaurant/zones is read-only and tenant-scoped.
- POST /api/delivery/quote uses the same quoteDelivery service as checkout, with real menu/option prices, address ownership/version, opening hours, pauses and postal rules. It returns exact totals/line prices, the winning rule and a quoteToken. X-Delivery-Quote is only a freshness comparison: checkout recomputes all values server-side. Missing/inactive coverage returns 422; below minimum returns 422; closed kitchen/stale quote/address revision returns 409 (deleted/foreign saved address 404). There is no wildcard coverage, distance calculation, live geocoding or paid maps.
- New checkouts require postalCode plus deliveryAddress or a savedAddressId (optional addressVersion). Order snapshots include original shipping text/postal details/instructions, zone ID/version, exact fee and payout. Replay precedes current eligibility/address lookup, so later address edits/removal, zone archival or fee changes cannot reprice or duplicate an existing order. Legacy no-postal retry keys are retained when upgrading the same intent; changed new postal/saved-address intent still conflicts under an existing key.

## Recovery and notifications API

POST /api/auth/forgot-password {email}: generic 202; malformed requests 400. POST /api/auth/reset-password {token,password}: single-use link; 10–72 UTF-8-byte password; success signs out existing sessions. Neither endpoint returns tokens or reset URLs.
GET /api/notifications?page=1: own authorized history (20/page), unreadCount, nextPage. GET ?countOnly=1: count only. PATCH {id} or {all:true}: idempotent mark-read, foreign/inaccessible id 404. There is no arbitrary client event-creation API. ADMIN-only GET/POST /api/dev/mail lists local metadata/processes bounded due retries only when the protected local adapter is configured; no reset link is returned.

PATCH {id,version,role,active,reference,reason,confirmAdminGrant?}: authorized audited change; old sessions revoked, self-lockout/linked roles/open rider assignments protected.

## Quantity inventory

`GET /api/restaurant/inventory?page=0`: own active menu records and 50 immutable movements (nextPage). OWNER/MANAGER/MENU only; KITCHEN cannot count stock.
`PATCH /api/restaurant/inventory`: `{kind:"PRODUCT"|"OPTION",id,version,tracked,quantity,reference,reason}`. Available whole units 0..1,000,000; reason 5..300 characters; reference 8..100 safe characters. Current stockVersion is required; stale adjustments return 409. An exact reference replay returns existing evidence; changing its intent returns 409. Actor/session and tenant permissions are rechecked in the transaction.

Catalog includes sold-out variants/add-ons so clients cannot silently fall back to the base item. Delivery quotes and checkout validate aggregate product/selected-option demand. Checkout commits stock, reservations, immutable movements, financial snapshots and notifications atomically. Retry existing checkout keys before new stock checks. Stock quantities/prices from clients are never authoritative. No basket-only reservation or automatic timeout releases for COD.

Tracking starts off for existing records. Counts are available-to-sell units, excluding committed orders. Early pre-acceptance cancellation, final verified unpaid expiry or full processed refund restores original commitments once, including archived/tracking-disabled targets. Retryable failed/authorized/created payments keep stock committed; accepted/prepared/picked-up/returned food is never automatically restored. Untracked historical orders have no fabricated reservations. Operators must recount physically before enabling tracking or correcting stock. ONLINE remains disabled.

## Operator review cases

GET /api/cases supports bounded pagination, search (case/order ID; private summary only for ADMIN), status, kind, priority and mine=1. ADMIN receives queue metadata and active operator choices. Other roles receive only authorized order case IDs/type/status/public decisions; private summaries, notes, evidence, assignment, audit events and hashes are excluded. Restaurant support follows HISTORY permission; settlement reports/evidence require OWNER. Rider access follows the current assignment.
POST /api/cases: {orderId,kind,summary,reference,evidence:[]}. Kinds: DELIVERY_EXCEPTION, CUSTOMER_COMPLAINT, ORDER_DISPUTE, SETTLEMENT_DISPUTE, REFUND_REQUEST. Actual owned order required; references bind exact report intent. Evidence references are stored ORDER:id, OPERATION:id, PAYMENT:id or owner/admin SETTLEMENT:id records belonging to that order; arbitrary URLs and cross-order evidence are rejected.
GET /api/cases/:id returns authorized public status, or full immutable history to ADMIN.
PATCH /api/cases/:id (ADMIN): {action,version,reference,note,evidence:[],...}. UPDATE sets priority/active-admin assignment and IN_REVIEW or WAITING. NOTE appends private evidence without public notification. RESOLVE/REJECT require assignment to the deciding admin, IN_REVIEW and a separate publicReason. Terminal cases cannot be edited/reopened; use an authorized follow-up report. Exact successful retries return current case state without repeating effects; changed references/version races return409.
Resolutions: NO_CHANGE (acknowledgement only), RESUME_DELIVERY, CONFIRM_RETURN, RELEASE_DISPUTE, REFUND_APPROVED_DEFERRED and SIMULATED_CREDIT. Returns require an actual current picked-up issue, use existing order/commission reversal guards and never restore prepared stock, collect COD or fabricate rider earnings. Release requires an actual disputed commission and no other open settlement case for that order. Settlement reports hold commission balances transactionally. Rejection/NO_CHANGE do not silently release financial holds; use explicit release or the existing audited finance controls.
REFUND_APPROVED_DEFERRED records a decision only, never calls a provider or changes payment evidence. SIMULATED_CREDIT requires an isolated loopback development database, eligible customer case, positive exact Decimal amount and cumulative credits <=order total. It is a labeled internal development ledger, with no real payment, refund, commission, COD or rider settlement effect. Real ONLINE/refunds/external payouts remain disabled.
Trusted delivery incidents, payment-review/requested/failed-refund evidence and commission disputes create source-keyed cases in their original transactions. Existing authorized delivery/dispute resolutions and verified full refunds synchronize active source cases. Notifications contain generic status text only; public reasons are available through scoped case reads. No external mail is sent.
POST /api/cases/import (ADMIN, optional orderId) catches up real unresolved pre-feature delivery/payment/dispute records, <=50 per source per request. It appends case/audit/notifications only; missing sources and resolved source conditions produce no cases, and repeated imports cannot duplicate evidence. Repeat batches for larger backlogs. Import is explicit, not a GET side effect or background scan.

## Customer email verification

GET /api/auth/verification returns the signed-in user's status VERIFIED, PENDING or LEGACY_ALLOWED. Legacy access is an explicit compatibility exception, not proof of email ownership. New public registration sets emailVerificationRequired=true and atomically queues protected local instructions/audit when the local adapter is enabled. Login and /me return own verification metadata. New customer checkout checks persisted status inside the order transaction after existing-key replay. Browsing/cart, addresses, recovery, support and historical orders remain available. Existing restaurant/rider/admin access is not newly gated.
POST /api/auth/verification {email}: generic 202 for eligible, unknown, inactive, verified and throttled recipients; shared hashed account/global counters plus 60-second user-locked send cooldown. Eligible resends invalidate older VERIFY links. No tokens, URLs or outbox bodies are returned. Resends never change account email or verification status themselves.
POST /api/auth/verify-email {token}: authenticated account required; token must be 64 lowercase hexadecimal characters and belong to the current customer ID/current email/authVersion. Only SHA-256 hashes persist in EmailVerificationToken; raw URLs exist only in authenticated encrypted local outbox bodies and the protected CLI. Tokens expire after 30 minutes, are single-use and consumed transactionally under the user row lock. GET links do not verify; /verify-email strips the fragment and requires explicit confirmation. Wrong account, invalid/expired/used/revoked links share a generic error. Token attempts are rate-limited.
POST /api/auth/change-email {email,password}: CUSTOMER/current-password/session guard, five requests per 15-minute window. Existing address/access stay unchanged until CHANGE proof at the new address. Existing-target collisions return the same generic 202; no target account details. Proof atomically switches the address, sets verifiedAt, increments authVersion, consumes all verification tokens and old reset links, and records immutable security evidence/notification. Existing sessions are invalidated and the confirming session is cleared; sign in with the new email. User ID and historical orders remain unchanged. If another account claims the target first, confirmation fails closed.
AccountSecurityEvent records actual queued requests/confirmations with email hashes and append-only evidence; no passwords/raw tokens. EmailOutbox now accepts exactly one reset OR verification token, preserving existing recovery mail and durable delivery/lease/retry behavior. Admin local-mail HTTP remains metadata-only; customer/anonymous access is 404. Explicit local CLI preview rechecks token/user/session-version/expiry/state. All external email/ONLINE/refunds/payouts remain disabled.

## Reviews and promotions

GET /api/reviews: approved verified-purchase public reviews and live aggregate rating/count. Restaurant and item ratings are separate. Public DTO excludes customer/order IDs, moderation reasons/flags and private audit. Active customer plus DELIVERED/PAID order with COD receipt or verified captured/no-review/no-refund online evidence is required; refunded/ineligible orders drop out of live aggregates. view=mine exposes only current customer's own reviews and eligible historical deliveries; view=manage is ADMIN or current tenant HISTORY permission, with search/status/flag filters and 30-row pages.
POST /api/reviews: {orderId,productId?,rating:1..5,text,reference}. Customer must own the delivered/reconciled order and have bought the selected item. One restaurant review and one per purchased product per order. Text 10..1000 characters; no links; shared request throttles. First submission within 30 days of delivery; at most two edits in the first seven days after submission (also capped by the submission window). Every submission/edit is PENDING, never immediately included in ratings.
PATCH /api/reviews/:id accepts versioned edits or {action,version,reference,reason}: ADMIN APPROVE/REJECT; current restaurant/order staff FLAG for their tenant; author WITHDRAW. Flags never suppress an approved rating. Only admins moderate; approval rechecks purchase evidence, and edits re-enter moderation. Reference-bound CommerceAudit is append-only; GET /api/reviews/:id returns admin-only audit. Relevant moderation notifications contain no private text.
GET /api/promotions: public active/scheduled-eligible non-exhausted offers, optional restaurantId (global plus that restaurant). Terms include target/value/cap/minimum/account limit/expiry; individual eligibility is authoritative at quote/checkout. view=manage requires OWNER or ADMIN; search/pagination is tenant-scoped. POST creates; PATCH /:id edits current version or soft-archives with action=ARCHIVE. Code is immutable after creation, usage limits cannot be lowered below committed count, and references bind exact intent. GET /:id exposes own/admin configuration/audit only. Owner funding/scope cannot be forged by client restaurant IDs.
Checkout accepts optional couponCode (normalized uppercase). Quote response includes server discount and promotion policy snapshot; no client amount is trusted, one credit only/no stacking. See FINANCE.md for explicit post-tax funding/rounding policy. Serializable creation commits order, stock, redemption/counter, commission snapshot and notifications together. X-Checkout-Retry-Key on quote can recover an already-created owned order only when normalized intent matches; it returns stored totals/line snapshots with replayOnly=true. Fresh requests still validate current availability, schedule, budgets and account limits. Legacy no-code hashes remain unchanged. Successful checkout clears coupon intent; lost-response reload restores it for safe replay. Cancellation/refund never reinstates coupon usage or alters historical prices.
## PWA and bounded catalog — 2026-11-15

`GET /api/catalog`: default `limit=24`, maximum 48; optional `q` (100 characters, case-insensitive literal substring), exact `category` (60 characters), `restaurantId`, and opaque `cursor`. Reject unknown/repeated/invalid parameters. Returns `products`, `nextCursor`, page-local `categories`, and `limit`. ID keyset order uses existing primary/restaurant indexes; filter-bound watermark cursors avoid OFFSET, duplicate keys and later inserts during traversal. Live closures/availability can remove results; a bounded page may be empty with a usable next cursor. Do not interpret this as a permanently frozen stock snapshot.

Basket lookup: `GET /api/catalog?ids=id1,id2` accepts at most 48 unique IDs and cannot combine search/category/cursor. It applies current public availability. React keeps visible-page data separate from basket metadata; filters/page URLs and browser history survive navigation/reload without fetching every page. Missing items block partial checkout and can be removed. Existing checkout ordering, authoritative quotes and idempotency remain required.

`GET /api/catalog/retry?ids=...` additionally requires a current CUSTOMER session and `X-Checkout-Retry-Key`. It exposes fallback product/selected-option metadata only from that customer's own existing order, with unavailable/zero-stock flags. This lets an unchanged owned retry reach historical quote validation after archival/closure; it never authorizes a fresh purchase or exposes another customer's order. All API responses remain no-store.

`GET /api/restaurant/menu` shares bounded pagination/search, but binds access to the current restaurant and includes unavailable own dishes. Menu management has search/first/next controls. Categories use 50-row ID pages with `nextCursor` and explicit more-category controls; editing preserves an off-page current category. Inventory product pages use 24 rows, `stockCursor`, `q` and `productNextCursor`, independently of existing stock-history pagination. No migration was needed: existing primary and tenant/availability indexes are verified.

PWA links must appear in the actual document head, including the manifest and 192/512 PNG/maskable icons. See the [manifest reference](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Manifest). Production builds register `/sw.js` at root scope. Only generic `/offline.html`, three icon assets and query-free same-origin `/_next/static/` assets are cached (32 runtime entries, 2 MiB maximum per runtime resource). Credential-free fetches and private/no-store rejection protect public cache boundaries. APIs, RSC, image optimizer requests, navigation responses, checkout/account/payment/financial data and external resources are never cached. No offline order/payment queue exists.

Worker updates wait for explicit user action and never auto-reload the page. Old `shaikhs-public-*` versions are cleaned without deleting unrelated caches. Bump `public/sw.js` VERSION when precached offline/icon content changes. Registration/storage failures leave online operation available; offline navigation uses a generic non-sensitive reconnect page. Chrome structural installability is distinct from physical-device installation, which remains untested.
