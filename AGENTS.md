# Engineering instructions

SHAIKH'S is a Next.js App Router modular monolith: React storefront and role dashboards, route-handler APIs, Prisma/PostgreSQL. Read `IMPLEMENTATION_PROGRESS.md` before changes.

- Preserve working behavior and existing data. Make small, reviewable changes. No public deployment, real payments, database reset or destructive operations without explicit authorization.
- Keep TypeScript strict; validate request bodies with Zod and authorize on the server using the current database user. Never trust client totals or tenant identifiers.
- Money uses Prisma Decimal and PostgreSQL numeric(10,2). Checkout retries must retain their customer-scoped idempotency key. State changes must compare the observed state atomically and record history in the same transaction.
- Preserve legacy no-option basket ordering/request fingerprints across checkout upgrades. Send delivery quote versions separately via X-Delivery-Policy-Version; replaying an existing order must not reprice it or rotate its saved retry key.
- Address/zone rules: scope saved addresses to the current customer; serialize default changes with the customer's row lock. Quote and checkout must share quoteDelivery, use active restaurant postal rules (highest priority wins; active ties rejected), enforce minimums/hours and fail closed without coverage. Preserve shipping snapshots and legacy retry keys; X-Delivery-Quote is a freshness check, not a client-supplied price or payment proof.
- Razorpay Checkout is TEST-only and requires both valid server credentials and RAZORPAY_SANDBOX_VERIFIED=true after actual provider acceptance. Never set the real flag from mocks or expose secrets/NEXT_PUBLIC credentials. Only the public test key and server order/paise reach the SDK.
- User deferred payment onboarding: do not request PAN, KYC documents or provider credentials. Keep real ONLINE payments disabled until explicit onboarding approval; use labelled mock/signed fixtures only. Disposable development databases must visibly identify their orders/payments/revenue as simulated.
- Online retries must reuse the reserved application/provider order, reconcile before reopening, and block pending authorizations. SDK callbacks are not payment proof; only verified API/webhook state can confirm payment. Preserve the reload retry key and selected payment method.
- Scope restaurant reads/writes by owner and rider actions by assignment. Registration always creates CUSTOMER accounts. Never expose password hashes, secrets or cross-tenant data.
- Restaurant staff must pass restaurantAccess on every request: OWNER alone manages settings/team, MANAGER edits menu/orders, MENU edits menu, KITCHEN handles orders. Local invitations are email-bound, expiring and hashed; never log tokens.
- Archive menu records and snapshot configured prices/options. Rider earnings are unique per completed order; policy changes affect new quotes only. Payout receipts require reconciled eligible earnings, exact Decimal sums and reference-bound idempotency; never net COD cash into earnings automatically.
- Use forest green and warm almond/cream for customer pages, with restrained burnt-orange accents; preserve established operational dashboard tokens. Use consistent Lucide icons, deliberate typography, accessible controls and reduced-motion support. Do not fabricate reviews, delivery promises, GPS or restaurant photography claims.
- Do not log `.env`, personal addresses, passwords or cookies. Use placeholders in `.env.example`. Keep demo seed accounts local.
- Add migrations without editing applied migration history. Review SQL; use a disposable database for migration tests. Never run `db push` or reset against production.
- Keep src/lib/schema-readiness.ts in sync with committed migrations; readiness must fail for missing/incomplete history. db:diagnose is read-only and must never print connection strings. Error monitoring may send/log only allowlisted hashed metadata and generated references, never raw errors or user data.
- Validate with `npm test`, `npm run lint`, `npx tsc --noEmit`, `npx prisma validate`, `npm run build`. Run database and browser checks for affected flows; report blocked checks explicitly.
- Ownership: UI in `src/components` and `src/app/globals.css`; shared business rules in `src/lib`; server boundaries in `src/app/api`; schema/migrations in `prisma`. Coordinate ownership before parallel edits.
- Keep docs aligned with source, distinguishing implemented, tested and planned behavior. Update progress and test reports with exact results and the next action.
- Definition of done: functionality, authorization, financial/data correctness, errors, accessibility, responsive visual review and relevant tests are verified. A build alone is insufficient.
- Git was initialized on 2026-11-17 for the explicitly authorized PRIVATE GitHub publication. Preserve user changes; never force-push or publish publicly. Confirm the staged source and reachable history contain no secrets or private operational evidence before each push.

- Recovery: reset token rows contain SHA-256 hashes only; encrypt local email bodies with DEV_MAIL_KEY. Local preview requires disposable loopback DB/APP and explicit local adapter. Never expose links/tokens in HTTP responses or logs; no external delivery without a reviewed adapter. Reset password and authVersion increment/token consumption/security notification must commit together.
- Notifications: emit trusted text only inside authorized order transactions; unique recipient/event/version keys deduplicate retries. Recheck current tenant/assignment permissions on history/read updates. Keep visible-tab polling bounded with backoff; never imply local outbox delivery is real email.

- Restaurant finance: effective-date rules/snapshots and financial evidence are append-only. Use exact Decimal item amounts; keep tax/delivery excluded and unsupported discount/tax allocations and partial refunds under review (supported courtesy credits follow the explicit policy below). Settlement allocations must remain isolated by SIMULATED/MANUAL_RECEIPT mode; offset recovery balances, respect holds and reverse dependent records first. Only owners read own finance; only admins record financial actions. See docs/FINANCE.md; no external payout is initiated.

- Recovery tooling: backup manifests must be signed with a separate operator-only key; archives are confidential and require encrypted private storage. Restore only into NEW local shaikhs_disposable_restore_* databases; never add --clean/reset/existing-target overwrite. Migration preflight is read-only and requires a fresh matching backup plus explicit approval before existing-database deploy. Preserve post-snapshot financial events during recovery; never auto-repoint traffic.

- Account/restaurant lifecycle: only ADMIN reviews applications or changes account roles/status and tenant lifecycle. Bind applicants to current user, protect self/last-admin access and linked roles/open rider assignments, version-check and serialize decisions, invalidate sessions after account changes, and append immutable AdminAction evidence in the same transaction. Suspension must be enforced at discovery/checkout/tenant API boundaries, not only by UI or isOpen. Preserve orders, financial records, existing retry keys and current authorized rider/admin fulfillment.

- Stock: available units exclude committed orders. Product and selected variant/add-on tracking all apply; aggregate demands and deduct with stockVersion CAS inside the Serializable checkout transaction. Customer idempotency replay must precede current stock checks. Keep stockVersion separate from menu version. StockMovement is append-only; adjustment references are bound to exact input and tenant. Restore original reservations once only for cancellation/final verified expiry/full refund before acceptance; never automatically restock prepared/picked-up/returned food. Disabling/archiving does not erase commitments or block eligible restoration; never fabricate reservations for legacy/untracked orders.

- Operator cases: ADMIN is the operator role; recheck active role/session inside every write transaction. Require current case version and reference-bound immutable events, assigned IN_REVIEW ownership before terminal decisions, and separate public reasons from private notes/evidence. Reports and evidence require current order/tenant/assignment access. Source cases commit with real events; explicit bounded import may append cases from actual unresolved records but never rewrite source state. Case decisions never invoke external refunds/payouts or mark money paid/refunded. Simulated credit is isolated-local-only, capped cumulatively at order total, recorded separately from actual ledgers. Prepared returns reuse guarded cancellation/commission reversal and never restore stock; shared dispute holds require explicit safe release. Preserve existing authorized resolution paths and synchronize related cases.

- Customer email verification: new public registrations require a verified email before NEW checkout; existing rows remain explicitly LEGACY_ALLOWED, never backdated as verified. Keep login, browsing/cart, recovery and historical-order access available; idempotent checkout replay must precede verification checks. Verification links use hashed 32-byte tokens bound to current user ID, email, purpose, authVersion and expiry; consume under the user lock once. Email changes require current password and proof at the new address before switching, then revoke sessions and old reset/verification links. Reuse encrypted protected local outbox/CLI only; no raw tokens/links in HTTP/logs or external delivery. Audit actual requests/confirmations immutably; generic rate-limited resend/change-collision responses must not reveal account existence.

- Reviews/promotions: publish only ADMIN-approved reviews backed by delivered/reconciled owned orders, with separate restaurant/item aggregates and no seeded/fabricated ratings. Edits require renewed moderation; owners may flag own reviews but cannot approve or hide them. Keep immutable commerce audit and version/idempotency guards. One post-tax courtesy credit per checkout, fixed/percentage rounded half-up once and capped at eligible item subtotal or original delivery fee/max credit; recorded tax/item prices stay unchanged. Restaurant-funded credit cannot exceed pre-credit restaurant net and reduces payable; platform-funded credit does not. Preserve original rider payout. Usage is consumed only with atomic checkout and never reinstated on cancel/refund. Snapshot funding/rule/amount; retries must restore coupon intent and reuse historical owned quote/order before current eligibility checks. No external payments/messages/payouts.

- PWA: cache only the explicit generic offline page/icons and same-origin immutable static resources. Never cache APIs, RSC, account/checkout/payment/financial data or navigation responses. Reject private/no-store responses; bound caches, preserve unrelated cache namespaces, bump public/sw.js VERSION when precached assets change, and never auto-reload an in-flight checkout on update. Keep manifest discovery links in the actual document head; browser emulation does not prove physical installation.
- Catalog: public/tenant menu reads are bounded (default 24/max 48), ordered by indexed ID with filter/tenant-bound snapshot cursors. Never fetch every page automatically to populate a basket. Hydrate at most 48 explicit product IDs; historical fallback requires the current customer's own checkout key and never authorizes a fresh purchase. Preserve original checkout item ordering and server-authoritative availability/quotes. Browser fixtures search their unique namespace rather than assuming an unbounded catalog response.

- Performance acceptance: keep managementRequest in src/lib/management-client so public readers do not eagerly import role-management UI. Measure production builds with isolated browsers and pinned Lighthouse/Web Vitals tools; reject host-injected reports, retain outliers/raw runs and distinguish simulated LCP/TBT from observed INP and field percentiles. Physical installation needs actual device evidence. Normal-motion accessibility scans must wait for finite entrance animations to settle without disabling their assertions.

- Catalog snapshot cutoffs must use the PostgreSQL clock that creates Product.createdAt; an application-clock cutoff can omit newly committed rows. Keep cursor cutoff stable across subsequent pages and preserve bounded keyset reads.
